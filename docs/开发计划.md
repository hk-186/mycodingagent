## 1. 背景与现状

当前 `deep_agent.py` 已跑通的能力：

- 基于 `deepagents.create_deep_agent` 的深度任务 Agent
- 虚拟文件系统（`FilesystemBackend`，写入 `deep_agent_workspace/`）
- 子代理机制（calculator 计算子代理）
- 双轨记忆：`SqliteSaver`（短期对话历史）+ `SqliteStore`（长期用户信息）
- Tavily 联网搜索（配置密钥后启用）
- LangSmith 追踪、流式 CLI 输出、会话管理命令

**定位判断**：这是一个完成度很高的 deepagents 学习 Demo，但本质是**通用深度任务助手**，还不是 coding agent。

根本区别：

- 通用助手的循环：想 → 说 / 写文件
- **Coding agent 的灵魂循环：想 → 改代码 → 运行验证 → 读错误 → 再改**，并且要在用户的真实 Git 仓库里安全工作

目前缺失的恰恰是「执行命令 → 拿到错误 → 修复 → 重新验证」这条闭环，以及配套的安全机制。

## 2. 目标：一个好的 AI Coding Agent 需要什么

### 2.1 九层能力架构

| 层            | 核心能力                                                           | 说明                              |
| ------------ | -------------------------------------------------------------- | ------------------------------- |
| 1. 模型层       | Function calling 可靠性、超时/重试、多模型 fallback、低 temperature          | coding 场景 temperature 一般 0\~0.2 |
| 2. Agent 循环层 | 规划→执行→观察→再规划；步数/递归/token 上限；中断恢复                               | 「自己的 agent」的核心，最终应自己掌控循环        |
| 3. 工具层       | Shell 执行、精确编辑（str\_replace）、代码搜索（grep/glob/AST 符号）、查看诊断、Git 操作 | 与通用助手差异最大的一层                    |
| 4. 验证闭环      | 运行测试/构建 → 捕获 exit code + stderr → 自动定位 → 修复 → 重跑直到通过           | coding agent 能力分水岭              |
| 5. 上下文管理层    | repo map、按需检索、长历史摘要、token 预算                                   | 决定能否在大型真实仓库工作                   |
| 6. 记忆层       | 项目约定（AGENTS.md）、用户偏好、会话检查点；按项目命名空间隔离                           | 现有雏形方向正确，需改造                    |
| 7. 安全权限层     | 路径越界防护、命令黑白名单、危险操作人工审批、diff 预览                                 | 能跑 shell 就必须有这层                 |
| 8. 人机协作层     | Plan 模式（先批后做）、执行中提问、进度/Todo 展示                                 | <br />                          |
| 9. 可观测与评估层   | 结构化事件流、trace、token 成本统计、任务 eval 回归集                            | 没有 eval，迭代全靠手感                  |

外围接口演进顺序：CLI → TUI → API（SSE）→ IDE 插件。

### 2.2 不可妥协的设计裁决

1. **先打通「在真实仓库里改代码并验证」的最小闭环**，多代理、语义检索、IDE 插件等全部往后排。
2. 任何 shell 写操作 / 危险命令必须经过权限层，默认不自动执行破坏性操作。
3. 所有长任务必须有步数、递归深度、token 三重预算，超限即停并汇报。
4. 配置一律走环境变量 / 配置文件，禁止在代码中硬编码密钥、base\_url、模型名。
5. 每一次对 Agent 本身的改动，都要能被 eval 回归集验证，而不是凭感觉判断好坏。
6. 不在用户仓库里做未告知的破坏性 Git 操作（reset --hard、clean、force push 等）。

实际产出：

- **审批与命令分级**：`permissions.py` 在阶段 1 的 `check_command` 黑名单基础上新增 `ApprovalDecision` 数据类与 `classify_command(command)`，把命令分到三档——`block`（黑名单命中）、`needs_approval`（灰区：单文件删除、git reset --mixed、修改权限、卸载包、杀进程等）、`allow`（常规安全命令）。黑名单仍由 `SafeShellBackend` 兜底拦截，确保即使审批配置被绕过也不会真正执行递归强删。
- **审批策略谓词**：新建 `approvals.py`，提供 `should_interrupt_command(tool_call_request)` 作为 deepagents `InterruptOnConfig.when` 谓词。组合 `config.APPROVAL_MODE`（minimal / all / disabled 三档）与 `config.PLAN_MODE`：`disabled` 永不审批（黑名单仍兜底）、`minimal` 仅危险+灰区审批、`all` 所有写命令审批；`PLAN_MODE=True` 时所有写命令一律审批，读命令放行，优先级最高。
- **deepagents 原生 HITL 接入**：`agent.py` 通过 `create_deep_agent(interrupt_on={...}, permissions=...)` 接入 `HumanInTheLoopMiddleware`——在 AIMessage 后、工具执行前由中间件调 `langgraph.types.interrupt(HITLRequest)` 暂停图。配置了四个 `InterruptOnConfig`：
  - `execute`：`when=should_interrupt_command`（条件触发），`allowed_decisions=["approve","reject"]`，`description=_execute_description_factory` 渲染待执行命令；
  - `git_commit`：`allowed_decisions=["approve","reject"]`，`description=_commit_description_factory` 渐进取 `git status --short --branch` + `git diff --cached --stat` 拼摘要；
  - `ask_user`：`allowed_decisions=["respond"]`，由用户 `respond` 决策代答（工具体本身 `return ""` 永不执行）；
  - `propose_plan`：`allowed_decisions=["approve","reject"]`，Plan 模式下提交计划等审批（工具体 `return "计划已批准"` 永不执行）。
  - 子代理 `calculator_subagent` 显式 `"interrupt_on": {}` 禁用继承。
- **Git 工具**：新建 `tools/git_tools.py`，`_run_git(args)` 内部 `subprocess.run(["git", *args], cwd=config.PROJECT_DIR, capture_output=True, encoding="utf-8")`，绕开 `SafeShellBackend` 黑名单（git 写命令应由本层审批，不应被兜底拦截）。`git_status` / `git_diff` / `git_log` 只读直接执行；`git_commit(message)` 先检查暂存变更（无暂存时提示先 `git add`，无变更直接拒绝），然后真正 `git commit -m <message>` 并展示 `log -1 --stat` 作为确认。
- **ask_user 工具**：`tools/ask_user.py` 的 `ask_user(question)` 工具体本身 `return ""`，被 `interrupt_on` 拦截后 `ActionRequest` 推给 CLI，用户 `respond` 决策的回答文本作为 `ToolMessage.content` 返给模型，工具执行被跳过。
- **propose_plan 工具**：`tools/plan.py` 的 `propose_plan(plan)` 同样被 `interrupt_on` 拦截，Plan 模式下用于提交计划等审批；被 reject 时由中间件生成 error `ToolMessage` 引导模型重规划。
- **事件流扩展**：`events.py` 新增 `INTERRUPT` 事件类型与 `STOP_PENDING_INTERRUPT` 常量；`AgentEvent` 加 `action_requests: list[dict]` 与 `interrupt_id: str` 字段；新增纯函数 `detect_pending_interrupt(agent, cfg)` 通过 `agent.get_state(cfg).interrupts`（LangGraph 1.x 稳定 API）读取 pending interrupt；`iter_task_events` 加 `resume_decisions` 参数，resume 时构造 `Command(resume={"decisions": [...]})` 让图从断点继续；stream 自然结束后调 `detect_pending_interrupt`，非空则产出 `INTERRUPT` 事件并 return（不产出 summary，等 CLI resume 后再收尾）。`render_event` 加 `INTERRUPT` 渲染：列出每个 action_request 的 name/args/description，提示 `/approve | /reject <reason> | /respond <text>`。

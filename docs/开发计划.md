## 1. 背景与现状

当前 `deep_agent.py` 已跑通的能力：

- 基于 `deepagents.create_deep_agent` 的深度任务 Agent
- 虚拟文件系统（`FilesystemBackend`，写入 `deep_agent_workspace/`）
- 子代理机制（calculator 计算子代理）
- 双轨记忆：`SqliteSaver`（短期对话历史）+ `SqliteStore`（长期用户信息）
- Tavily 联网搜索（配置密钥后启用）
- LangSmith 追踪、流式 CLI 输出、会话管理命令

**定位判断**：这是一个完成度很高的 deepagents 学习 Demo，但本质是**通用深度任务助手**，还不是 coding agent。

根本区别：

- 通用助手的循环：想 → 说 / 写文件
- **Coding agent 的灵魂循环：想 → 改代码 → 运行验证 → 读错误 → 再改**，并且要在用户的真实 Git 仓库里安全工作

目前缺失的恰恰是「执行命令 → 拿到错误 → 修复 → 重新验证」这条闭环，以及配套的安全机制。

## 2. 目标：一个好的 AI Coding Agent 需要什么

### 2.1 九层能力架构

| 层            | 核心能力                                                           | 说明                              |
| ------------ | -------------------------------------------------------------- | ------------------------------- |
| 1. 模型层       | Function calling 可靠性、超时/重试、多模型 fallback、低 temperature          | coding 场景 temperature 一般 0\~0.2 |
| 2. Agent 循环层 | 规划→执行→观察→再规划；步数/递归/token 上限；中断恢复                               | 「自己的 agent」的核心，最终应自己掌控循环        |
| 3. 工具层       | Shell 执行、精确编辑（str\_replace）、代码搜索（grep/glob/AST 符号）、查看诊断、Git 操作 | 与通用助手差异最大的一层                    |
| 4. 验证闭环      | 运行测试/构建 → 捕获 exit code + stderr → 自动定位 → 修复 → 重跑直到通过           | coding agent 能力分水岭              |
| 5. 上下文管理层    | repo map、按需检索、长历史摘要、token 预算                                   | 决定能否在大型真实仓库工作                   |
| 6. 记忆层       | 项目约定（AGENTS.md）、用户偏好、会话检查点；按项目命名空间隔离                           | 现有雏形方向正确，需改造                    |
| 7. 安全权限层     | 路径越界防护、命令黑白名单、危险操作人工审批、diff 预览                                 | 能跑 shell 就必须有这层                 |
| 8. 人机协作层     | Plan 模式（先批后做）、执行中提问、进度/Todo 展示                                 | <br />                          |
| 9. 可观测与评估层   | 结构化事件流、trace、token 成本统计、任务 eval 回归集                            | 没有 eval，迭代全靠手感                  |

外围接口演进顺序：CLI → TUI → API（SSE）→ IDE 插件。

### 2.2 不可妥协的设计裁决

1. **先打通「在真实仓库里改代码并验证」的最小闭环**，多代理、语义检索、IDE 插件等全部往后排。
2. 任何 shell 写操作 / 危险命令必须经过权限层，默认不自动执行破坏性操作。
3. 所有长任务必须有步数、递归深度、token 三重预算，超限即停并汇报。
4. 配置一律走环境变量 / 配置文件，禁止在代码中硬编码密钥、base\_url、模型名。
5. 每一次对 Agent 本身的改动，都要能被 eval 回归集验证，而不是凭感觉判断好坏。
6. 不在用户仓库里做未告知的破坏性 Git 操作（reset --hard、clean、force push 等）。

### 阶段 1 · Coding 工具最小集（核心，2\~4 天）✅ 已完成（2026-09-29）

- [x] `shell` 工具：指定 cwd、超时控制、exit code 返回、stdout/stderr 截断

- [x] `view`（带行号区间读取）、`grep` / `glob` 代码搜索工具
- [x] `todo` 工具：任务清单写入 agent state，执行中实时更新

实际产出：`permissions.py`（危险命令黑名单）、`tools/shell.py`（SafeShellBackend =

工作目录优先级：CLI `--project` > 环境变量 `AGENT_PROJECT_DIR` > 默认 `workspace/`。

**验收标准**：对一个真实小仓库，用自然语言让 Agent 完成「新增一个函数 + 运行脚本验证」的完整任务。

Agent 自主完成「新增 `is_palindrome`（casefold 支持中文）→ 运行 `python run_checks.py` →

### 阶段 2 · 验证闭环（2\~3 天）

- [ ] Agent 循环加入：改完 → 自动运行测试/构建 → 解析 stderr → 再修，最多 N 轮
- [ ] 设置 `recursion_limit`、每任务步数上限与 token 预算，超限停下并汇报
- [ ] 流式输出重构为结构化事件（`tool_start` / `tool_end` / `assistant_message` / `error`）
- [ ] 支持中断后 `/resume` 继续（复用现有 checkpoint 基础）

**验收标准**：给一个含 1 个失败测试的仓库，Agent 能自动定位、修复并让测试转绿；中途超限会安全停下而不是无限循环。

### 阶段 3 · 安全与人机协作（2\~3 天）

- [ ] 写操作（shell 危险命令、文件编辑）默认 diff 预览 + 审批钩子
- [ ] Plan 模式：先输出改动计划，用户批准后才动手
- [ ] 执行中提问工具：信息不足时主动澄清而不是瞎猜
- [ ] Git 工具：`status / diff / log / commit`，提交前展示变更摘要

**验收标准**：Agent 尝试删文件或执行危险命令时被拦截，等待用户确认；Plan 模式下未批准前仓库零改动。

### 阶段 4 · 代码库规模化（3\~5 天）

- [ ] ripgrep 级文本搜索 + AST 符号检索（Python 用 `ast` / tree-sitter）
- [ ] repo map：自动生成模块/类/函数地图辅助定位
- [ ] 上下文预算管理：大文件分页读、历史摘要、工具结果裁剪

**验收标准**：在中大型（几十万行）仓库中完成跨文件小改动，定位准确且不撑爆上下文。

### 阶段 5 · 记忆与多代理（2\~4 天）

- [ ] 记忆按项目命名空间隔离；自动发现并加载项目根目录的 `AGENTS.md`
- [ ] 子代理替换为 `code-reviewer`（改动后自动 review）、`test-writer`（补测试）
- [ ] 修复 C13：长期记忆查询改用 store 索引能力而非全量扫描

**验收标准**：跨会话能记住项目约定；每次代码改动后自动收到 review 意见与测试补充建议。

### 阶段 6 · 可观测、评估与接口（持续）

- [ ] token / 成本 / 耗时统计；LangSmith 保留为可选 trace
- [ ] 建立 10\~20 个小任务的 eval 回归集（修 bug、加函数、重构），每次改 Agent 跑一遍
- [ ] TUI（Rich/Textual）→ FastAPI + SSE → 远期 IDE 插件

**验收标准**：每次 Agent 迭代都有 eval 分数对比，用数字证明变好还是变差。

### 5.1 关键技术练习：自研最小 Agent 循环

在阶段 1\~2 之间，用 LangGraph 的 `StateGraph` 手写一遍最小循环（模型节点 ↔ 工具节点，挂 shell/edit/todo），把 `create_deep_agent` 当参照实现。

目的：把循环控制权、审批节点、预算中断、事件流掌握在自己手里，避免后续高级特性被框架卡住。这是从「用框架搭 Demo」走向「做自己的 Agent」的分水岭。

## 6. 风险与对策

| 风险              | 对策                                                        |
| --------------- | --------------------------------------------------------- |
| Shell 执行造成误删/误改 | 阶段 1 即内置危险命令拦截；阶段 3 上审批与 diff 预览；只在 Git 仓库内工作，改动可经 Git 回滚 |
| 长任务失控、token 超支  | 阶段 2 落地步数/递归/token 三重预算                                   |
| 模型 API 不稳定或限流   | timeout + 重试 + 多模型 fallback（阶段 0 预留配置位）                   |
| 大仓库上下文爆炸        | 阶段 4 的 repo map + 分页读取 + 摘要，禁止整库灌入                        |
| 框架能力受限          | 阶段 1\~2 间自研 StateGraph 循环，deepagents 仅作参照                 |
| 迭代引入退化          | 阶段 6 eval 回归集先行，改 Agent 必跑 eval                           |
